一个原则贯穿全图：核心只认识"事件"，不认识任何数据源。所以换学校、换白板、换操作系统，改的都是外围。

a-screen

希沃那一屏：Windows 走 GDI BitBlt 或 DXGI 桌面复制，Linux 走 X11 GetImage（有合成器时抓 Composite overlay，否则抓根窗口）→ 只在画面真变了时落一张 PNG。两道门限是“或”关系： dHash（≤ 64）认结构变化但看不见整块黑变白，均差（≤ 255）补这一刀。不做连续视频。 source:"fixture" 回放一排 PNG 走同一套判定；Windows runner 上 gdi 真开到一块 1920×1080 桌面并落了一张真 PNG（61 次询问里 60 次判为“无变化”），Linux runner 上 CI 起 Xvfb、改两次底色，断到 x11 真采到 1280×720 且两次变化都被看见。 Wayland 会话明确拒绝（XWayland 根窗口不是整块桌面），PipeWire 后端未实现。 未实测：真一体机上的 gdi/dxgi、真 X11 桌面、多屏选择与 DPI

③ 出机器：一节课到底传多少

音频

Opus 16k 单声道 45 分钟 ≈ 5–10 MB（实测 300 段 / 9.2 MB 未压缩 PCM 口径）

事件

笔迹+评估+健康 ≈ < 1 MB。带宽从来不是瓶颈

屏幕

只存变化时刻的关键帧，不存视频。一张 1080p 全屏 PNG 实测 ≈ 2.3 MB（不降采样的时候），所以帧数是唯一体积变量：一节课存多少张由两道门限与 min_interval_ms 决定，max_width / max_frames / max_bytes 可封顶；撞顶不丢数据，而是在收课记录里记 capped，健康表与摘要会直说“之后的画面没存档”

视频

1080p 一节课 1.35–2.7 GB，是音频的 150–300 倍 → 一旦要做连续视频，架构被迫上边缘盒。我们没有边缘盒，所以不做

④ 两道边界，是这套设计里唯一"必须正确"的东西

CI 断言

文件边界

看板的 blob 接口是唯一能把 GET 变成"读一体机任意文件"的口子。lesson id 与 blob 名都过白名单 （禁 / \ .. NUL），四类穿越在 Win/Linux 上都回 400

CI 断言

数据边界

永不静默丢数据：坏行进 Rejected 并留原文，跳号进 GapBefore 并计丢失条数， 超预算只标记不丢弃。开着课 0 事件满 5 秒直接告警

还没证明的事："低开销"目前只测到事件总线（真实节奏 0.02% CPU / 11 MB 工作集，Core Ultra 5 226V，非一体机）。 音频编码未实现；屏幕采集已在 Windows runner（GDI）与 Linux runner（Xvfb + X11）上真采到过帧，但从未在目标一体机上跑过（多屏 / DPI / 长时间连续板书都是 fixture 与 Xvfb 供不了的），而它们才是开销主体； 目标一体机是 8 代 i5 级 CPU + 红外无压感触控，很多前提还没在真机上确认。
